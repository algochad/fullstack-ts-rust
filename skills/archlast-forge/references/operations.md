# Operations: configuration, the stack, deployment, scaling, backups, upgrades, troubleshooting

Read this when you configure the engine (env vars, settings), containerize or deploy an app, scale past one server, back up or restore data, upgrade versions, or diagnose a failure to start or serve. Every command and flag in full: [cli.md](cli.md). Features these settings control: [server-features.md](server-features.md).

## Most used commands

Run through package scripts (`bun run dev`) or `bunx archlast-forge <cmd>`; they act on the project found from the cwd (`forge/schema.ts`) or `--dir <forge dir>`. Failures print `✗ <message>` and exit 1.

| Goal                                                                | Command                                                                                    |
| ------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| Develop (live reload, dashboard, services in Docker)                | `archlast-forge dev` (`--no-docker` for SQLite only, `--port`, `--with postgres,redis,s3`) |
| Regenerate `forge/_generated` after editing functions or the schema | `archlast-forge codegen` (or `bun run typecheck`, which runs codegen then `tsc`)           |
| Build the production image / the full-stack bundles without Docker  | `archlast-forge build [--tag <image>]` / `build --no-docker`                               |
| Run the whole stack (app + services) / stop it                      | `archlast-forge up [--rebuild]` / `down [--volumes]` (`--volumes` deletes the data)        |
| Follow logs, see containers                                         | `archlast-forge logs [app]` / `status`                                                     |
| Run in production without Docker                                    | `archlast-forge start --no-docker` (or `start --image <tag>`)                              |
| Check/sync tables, run data migrations                              | `archlast-forge migrate [--status \| --run-migrations]`                                    |
| Full backup / restore                                               | `archlast-forge backup app.tar.gz` / `restore app.tar.gz [--config]`                       |
| Move documents                                                      | `archlast-forge export f.jsonl` / `import f.jsonl [--replace]`                             |
| Function env vars (stored in the database)                          | `archlast-forge env set NAME value`, `env list`, `env get`, `env rm`                       |
| Dashboard accounts                                                  | `archlast-forge admin add you@x.com --role owner`, `admin list`, `admin remove`            |
| Move to a release (monorepo moves whole)                            | `archlast-forge upgrade [version]`                                                         |
| Add/remove postgres, redis, s3, caddy                               | `archlast-forge stack add redis`, `stack remove caddy`                                     |

Data commands (`migrate`, `export`, `import`, `backup`, `restore`, `env`, `admin`) run **inside the running server** (so imports reach live subscribers): in the compose `app` container or a CLI-started engine container via `docker exec`, else `POST /_cli` on `localhost:<port>` with `ADMIN_KEY` (dev key is read from `forge/data/.dev-secrets.json`), and only when nothing answers do they open the local SQLite file (or `DATABASE_URL`) themselves. In that last case a remote or Caddy-only stack is **not** touched and nothing warns you: run the command in the container.

## Configuration

The engine reads environment variables once at startup. Bad or contradictory values stop it with a one-line message (table at the end of the deployment section). Your own function code reads `process.env`.

### Where values come from

| You run                                            | Settings from                                                                                                                   | Data in                          |
| -------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- | -------------------------------- |
| `dev` (full-stack, or `--no-docker`)               | process env + generated dev secrets                                                                                             | `forge/data/`                    |
| `dev` (backend, Docker)                            | `forge/.env` if present + values the CLI sets (`PORT`, `DATA_DIR`, secrets, `BETTER_AUTH_URL`, `TRUSTED_ORIGINS`, service URLs) | Docker volume at `/data`         |
| `start --no-docker`                                | process env (Bun also loads `.env` from the cwd)                                                                                | `forge/data/`, unless `DATA_DIR` |
| `up` / `start` (project has `archlast-forge.json`) | `.env` in the project root, **through `compose.yaml`**                                                                          | volume `app-data` at `/data`     |
| `start --image <tag>`                              | `forge/.env` or `--env-file`                                                                                                    | volume `<name>-data` at `/data`  |

Precedence, highest first: **process environment**, then values saved on the dashboard's Settings page (`_settings` table; owners only), then defaults. The environment is never overwritten by the CLI, `env set` or the dashboard; a variable set there shows read-only on the Settings page.

- **`compose.yaml` passes the app only what it lists** under `environment:`: `BETTER_AUTH_SECRET`, `ADMIN_KEY`, `BETTER_AUTH_URL`, `ALLOW_INSECURE_HTTP`, `DASHBOARD` (default `on` in the stack), `OTEL_SERVICE_NAME` (empty by default: the service name, also the start of its Redis keys), `DATABASE_URL`/`REDIS_URL`/`REDIS_PREFIX`/`S3_*` for chosen services, and with Caddy `TRUST_PROXY=1` and `TRUSTED_ORIGINS=https://${DOMAIN}`. To set anything else (`RATE_LIMIT_PER_MINUTE`, `LOG_FORMAT`, `RUNTIME_WORKERS`, `TRUSTED_ORIGINS` without Caddy, `TRUST_PROXY` without Caddy), add `NAME: "${NAME:-}"` to `environment:` and put the value in `.env`. `.env` alone does nothing.
- **Env-only** (the Settings page cannot change them): `PORT`, `HOST`, `DATA_DIR`, `DATABASE_URL`, `REDIS_URL`, `REDIS_PREFIX`, `REPLICAS`, `BETTER_AUTH_URL`, `BETTER_AUTH_SECRET`, `ADMIN_KEY`, `DASHBOARD`, `FORGE_RPC_TOKEN`, `MICROSERVICES`, `DASHBOARD_URL`, `DASHBOARD_TOKEN`.
- **Live** (apply within seconds, no restart): the `BACKUP_*` settings, the security headers (`HELMET`, `HELMET_CONFIG`) and the firewall (`WAF`, `WAF_*`: new threads load the rules first, so rules that can't load change nothing). `RUNTIME_WORKERS`/`RUNTIME_WORKERS_RATIO` resize the pool at once in `process` mode. **Everything else saved on the dashboard applies after a restart** (the page has Restart now; the CLI restarts in place).
- Formats: integers are whole numbers at or above the minimum (`"10s"` is rejected); booleans are true only for `1`, `true`, `on`, `yes` (`DASHBOARD=enabled` is **off**: write `on`/`off`); lists are comma separated; an empty value means default.
- Dev secrets: `dev` generates `BETTER_AUTH_SECRET` and `ADMIN_KEY` once into `forge/data/.dev-secrets.json` (mode 0600) unless already in the environment. Nothing is generated outside dev; `up` makes `.env` once with fresh secrets and never rewrites it.
- `archlast-forge.json`: `{ "mode": "framework" | "backend", "services": [...] }`. `services` is what `dev` starts and what compose files were generated for; editing it does not rewrite `compose.yaml` (use `stack add/remove`).

### Dev defaults versus production defaults

Most "works in dev, breaks in production" reports are one of these. "Production" is everything except `archlast-forge dev` (so `start`, `up` and the image too).

| Setting                                           | `dev`                                     | Production                                                                         |
| ------------------------------------------------- | ----------------------------------------- | ---------------------------------------------------------------------------------- |
| `BETTER_AUTH_SECRET`, `ADMIN_KEY`                 | generated                                 | you must set them (the secret is required)                                         |
| `BETTER_AUTH_URL`                                 | `http://localhost:<port>`                 | must be https (or `ALLOW_INSECURE_HTTP=1`)                                         |
| `DASHBOARD`, `ALLOW_CUSTOM_FUNCTIONS`, `API_DOCS` | on                                        | off (the generated compose turns the dashboard on; `http.docs({ production: true })` serves the docs) |
| Postgres pools                                    | 4 read + 8 write per runtime process      | sized from `max_connections`                                                       |
| HSTS, `upgrade-insecure-requests`                 | not sent                                  | sent when `BETTER_AUTH_URL` is https                                               |
| `RATE_LIMIT_PER_MINUTE`; Better Auth's own limits | off                                       | 1200; on                                                                           |
| `SCHEMA_CHECK`                                    | off                                       | on: startup refuses mismatching documents                                          |
| `STORAGE` without S3                              | `local` (`DATA_DIR/storage`)              | `off`: `ctx.storage` throws until `STORAGE=local` or S3                            |
| `RUNTIME_MODE`                                    | `process` (reloads code on save)          | `inline` (functions in the server process)                                         |
| `LOG_FORMAT`; error text to callers               | `pretty`; real messages                   | `json`; `Server error (request <id>)` for anything but `ForgeError` and validation |
| `TRUSTED_ORIGINS`                                 | defaults to `http://localhost:<port>`     | none unless you set it                                                             |
| A module that fails to load                       | server stays up, `/ready` is 503, retries | the process exits                                                                  |

### Variables for your own functions

Two places: the server's environment (shell, `.env`/`compose.yaml`, platform secret store) or the **`_env` table** via `archlast-forge env set NAME value` (names `[A-Za-z_][A-Za-z0-9_]*`; travels with backups; no rebuild).

- The process environment wins: at load each `_env` row is copied into `process.env` only if the name is not already set. A variable in `compose.yaml` overrides `env set`.
- `env set`/`env rm` ask the running engine to reload (SIGHUP to the container, or `/_admin/reload` of a local server). `(no running server picked it up; it applies on next start)` means nothing could be reloaded (dashboard off on a local server): restart.
- `env list` prints values to anyone with the admin key; the dashboard shows names only. Engine settings (`PORT`, `BETTER_AUTH_SECRET`, …) in `_env` never reach the engine; they are read before the database opens.
- A query that reads `process.env` is cached up to `CACHE_TTL_MS`; a reload clears the cache.

## The stack `init` generates

`archlast-forge init` (see [project-modes.md](project-modes.md)) writes the deployment next to your code. These files are **yours to edit**; `up` runs what you wrote.

| File           | Role                                                                                                                                                                                                                                                                                                                                           |
| -------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Dockerfile`   | `ARG ENGINE_IMAGE=ghcr.io/algochad/archlast-forge-engine:<version>`, `FROM ${ENGINE_IMAGE}`, `COPY . /src`, `RUN … engine prepare` (installs `forge/package.json` deps for Linux, codegen, and for full-stack apps builds the bundles), `ENV NODE_ENV=production`. No `.env` inside (`.dockerignore` excludes it).                             |
| `compose.yaml` | `app` (builds the Dockerfile, `restart: unless-stopped`, volume `app-data:/data`), plus the chosen services: `postgres:17-alpine` (user/db `forge`, healthcheck), `redis:7-alpine` (appendonly), `rustfs` + a one-shot `rustfs-init` that creates bucket `forge`, `caddy:2-alpine`. `app` waits for healthy dependencies.                      |
| `.env`         | Fresh secrets, mode 0600, created once by `up`. Keys: `BETTER_AUTH_SECRET`, `ADMIN_KEY`, `BETTER_AUTH_URL`, `POSTGRES_PASSWORD`, `S3_ACCESS_KEY`, `S3_SECRET_KEY`, `S3_PUBLIC_ENDPOINT`; without Caddy `ALLOW_INSECURE_HTTP=1`, `PORT=3000`, `S3_PORT=9000`; with Caddy `DOMAIN`. Keep it out of git. `.env.example` has the same keys, empty. |
| `Caddyfile`    | `{$DOMAIN:localhost} { encode zstd gzip; reverse_proxy app:3000 }`, plus `s3.{$DOMAIN}` -> `rustfs:9000` when storage is on. Certificates are automatic once DNS points at the machine and ports 80/443 are free.                                                                                                                              |

Facts that bite:

- Without Caddy the app publishes `${PORT:-3000}:3000` and RustFS `${S3_PORT:-9000}:9000`; **with Caddy nothing but 80/443 is published**.
- Without Caddy `.env` sets `BETTER_AUTH_URL=http://localhost:3000` plus `ALLOW_INSECURE_HTTP=1`: fine to try, **not** for real users. Switching to https means a real `BETTER_AUTH_URL`, removing `ALLOW_INSECURE_HTTP`, and `TRUST_PROXY=1`.
- With Caddy: set `DOMAIN` (and DNS for `DOMAIN` and `s3.DOMAIN`), `BETTER_AUTH_URL=https://${DOMAIN}`; compose already sets `TRUST_PROXY` and `TRUSTED_ORIGINS`. `DOMAIN` must appear **above** lines that use `${DOMAIN}` in `.env`.
- `RUSTFS_CORS_ALLOWED_ORIGINS` is `*` in the generated file: narrow it to your origins for production.
- `up`: builds the image, `docker compose up -d --wait` (up to 240 s), prints URLs. `down` keeps volumes. Volume names derive from the compose `name:`; renaming it creates a new empty project.
- `stack add|remove <list>` rewrites `archlast-forge.json`, `.env` keys, and regenerates `compose.yaml`/`Caddyfile` only if they are still what the old services would have produced (else it writes `compose.new.yaml` to merge). It never moves data between SQLite and Postgres (`export` before, `import` after).
- Without the compose file, `docker compose up -d --build` works the same where the CLI is not installed (set `ENGINE_IMAGE` if you mirror the engine image).

## Deployment

Self-hosted: one deployment per app. The deployable is one container image (engine + your code); around it Postgres, Redis, S3, a TLS proxy as needed.

| Path                                                                                                                                                                                            | Use                                                                                  |
| ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| `archlast-forge up` on a Docker host (the tested path)                                                                                                                                          | VPS: copy the project and `.env`, point DNS, run `up`. Updating is the same command. |
| `build --tag my-app:1.0`, then `start --image my-app:1.0 --env-file .env.production --port 3000` or `docker run -d --restart unless-stopped -p 3000:3000 -v data:/data --env-file … my-app:1.0` | Your own orchestrator.                                                               |
| `build --no-docker`, `start --no-docker` under systemd (`Restart=always`, `TimeoutStopSec=30`, `EnvironmentFile=`)                                                                              | A machine with Bun 1.4.4+; set `DATA_DIR` on a persistent disk.                      |
| Platforms that terminate TLS for you (Coolify, Fly.io, Kubernetes ingress)                                                                                                                      | Untested guidance, below.                                                            |

**Production environment, minimum:** `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL=https://…`, `ADMIN_KEY`, `TRUST_PROXY=1` (behind a proxy), `TRUSTED_ORIGINS` (only if another origin calls the API with cookies), `DASHBOARD=off` unless you use it behind a fence, `DATABASE_URL`/`REDIS_URL`/`S3_*` as needed. The image runs with `NODE_ENV=production`, listens on 3000, has a Docker `HEALTHCHECK` on `/health`, stores state under `/data`. It is Bun on distroless with BusyBox (`/bin/sh` works) and has **no `apt-get`**: never write `RUN apt-get install` in a project's `Dockerfile`; copy a static binary in with `COPY --from=<image> <path> /usr/local/bin/`.

**TLS and proxies.** The engine speaks plain HTTP; terminate TLS in front. Any proxy must: pass WebSocket upgrades on `/rpc` (HTTP/1.1, `Upgrade` and `Connection` headers; Caddy does it by default, nginx needs them set, `proxy_read_timeout` high); keep idle upstream connections shorter than `IDLE_TIMEOUT_SECONDS`; set `X-Forwarded-For` (and the engine reads only the **last** entry, one proxy deep); **not rewrite paths**: `/rpc`, `/api/auth`, `/http`, `/_app`, `/_admin`, `/_dashboard` (its files are under `/_dashboard/_assets/`), the API docs' path (`/_api` or `http.docs({ path })`), `/_storage`, `/_csp`, `/health`, `/ready`, `/metrics`, `/otlp` must reach the engine under those names; allow request bodies at least `MAX_REQUEST_BYTES`; pass the S3 `Host` header unchanged. Do **not** add CSP, HSTS or X-Frame-Options at the proxy: the engine sets them (Helmet presets per surface), and a second copy from the proxy makes browsers apply both and break pages; change them with `http.helmet()` or the Security page. A frontend on another origin: either route `/rpc`, `/api/auth`, `/http` to the engine from its origin, or list it in `TRUSTED_ORIGINS` and create the client with `{ url }`; cookies are `SameSite=Lax`, so subdomains of one site work and unrelated sites do not.

**Platform checklist (Coolify, Fly, Kubernetes, others; the repo only documents Coolify for its own docs site, so treat this as untested):** build from the project's root `Dockerfile` (or compose without the Caddy service: `stack remove caddy`); container port 3000; set the secrets above in the platform's variable store (nothing secret in the image); `BETTER_AUTH_URL` = the public https URL; `TRUST_PROXY=1`; persistent volume on `/data` when on SQLite (one replica only) writable by uid 1000 (the engine runs as `bun`, not root; a volume an older root image made needs `chown -R 1000:1000` once), otherwise Postgres/Redis outside the container; readiness probe `GET /ready`, liveness `GET /health`; grace period 30 s; the platform's proxy must pass WebSockets on `/rpc`. Set `FORGE_RELEASE` if the platform provides no commit variable.

**Health and shutdown.** `GET /health` -> `200 {"ok":true}` while the process serves. `GET /ready` -> `200 {"ready":true}` once functions loaded, else `503 {"ready":false}` (also while shutting down; `error` with the load error in dev only). In dev a broken module shows here and retries; in production a module that fails to load at startup **stops the process**. `SIGTERM`/`SIGINT` drain: `/ready` turns 503, new requests get 503 `Server is shutting down`, WebSockets close with 1012 (clients reconnect), in-flight requests get up to 10 s; a second signal exits 1. `docker stop` waits 10 s by default: set `stop_grace_period: 30s`. `SIGHUP` reloads the function runtime without dropping connections.

**Before real users arrive:** (1) `BETTER_AUTH_SECRET` random 32+ chars, only in the secret store or a `0600` `.env`; (2) `BETTER_AUTH_URL` public https, no `ALLOW_INSECURE_HTTP`; (3) the engine port is reachable only through the proxy; (4) `TRUST_PROXY=1` iff the proxy overwrites `X-Forwarded-For`; (5) `TRUSTED_ORIGINS` lists only needed origins (never `*`), same for bucket CORS; (6) dashboard off or fenced, `ALLOW_CUSTOM_FUNCTIONS` off, named admin accounts; (7) `ADMIN_KEY` random and not shared; (8) every public function checks caller and row owner, helpers are `internal*`; (9) webhooks verify signatures; (10) `RATE_LIMIT_PER_MINUTE` fits your traffic, Redis set when several servers; (11) Postgres and Redis not published to the internet; (12) `LOG_FORMAT=json` collected, restart policy set, and **a backup has been restored at least once**.

**Startup checks** (one line, exit 1; fix and restart):

| Message                                                                                                                         | Fix                                                                            |

## Scaling out

One server with SQLite is the default and fine to start. For more:

1. `DATABASE_URL=postgres://…` (writes run serializable with retry; indexes build concurrently under an advisory lock, so replicas can start together). Or `mongodb://…` (a replica set; writes are snapshot isolation, not serializable, and conflicts retry). Back up with the engine backups or `pg_dump` / `mongodump`.
2. `REDIS_URL=redis://…`: the bus that tells other servers a table changed (each re-runs its own subscriptions), the shared query cache, shared rate-limit counters (Better Auth's included). It holds nothing durable. Everything is under this service's prefix (`archlast-forge:<OTEL_SERVICE_NAME>:`, or `REDIS_PREFIX`), so every server of a service shares its keys and several services can share one Redis without seeing each other's cache, topics or limits: give each service its own `OTEL_SERVICE_NAME` (the generated `compose.yaml` passes it on from `.env`). An app with no name uses `archlast-forge:`, as before; a second app with the same prefix is reported at startup (`another app already uses the Redis prefix`). While Redis is down each server counts rate limits on its own and shared cache reads are empty; calls keep working.
3. `REPLICAS=N` on every server: only a fail-fast guard; it starts nothing. Same `BETTER_AUTH_SECRET`, `ADMIN_KEY`, `DATABASE_URL`, `REDIS_URL` everywhere (the service name, `OTEL_SERVICE_NAME`, fixes the Redis prefix, so scaled instances of one service agree). Naming a service that had no name moves its keys: set `REDIS_PREFIX=archlast-forge:` on every server first to keep the old ones through a rolling upgrade. S3 storage (not `STORAGE=local`). Backups into a bucket (`BACKUP_S3_*`), because a folder is one server's disk.
4. A load balancer that supports WebSockets on `/rpc`; sticky sessions are not needed (sessions are cookies). Probe `/ready`; roll servers one at a time: old and new code share the database, so add before you remove and never rename function arguments in one step (a client calling a function an older server lacks gets `404`).
5. Schedulers: every server polls; jobs are claimed atomically (mutations exactly once, actions at most once); each cron slot is inserted once. Only the first runtime process of each server runs the scheduler, backups and schema check.
6. Scrape `/metrics` on every server (counters are per process); the dashboard is per deployment, so Observe data from every server (Nodes page) lands in the shared store on Postgres.

**Postgres connections.** A pool opens all its connections at its first query and keeps them, so each server holds `RUNTIME_WORKERS x (DATABASE_POOL_SIZE + DATABASE_WRITE_POOL_SIZE) + 3` (telemetry) from start, and `REPLICAS` servers that many times. Unset, the engine reads `max_connections` at start and takes 60% of what an ordinary role may open, split across `REPLICAS` and `RUNTIME_WORKERS` (a third reads, the rest writes, at most 2x cores reads and 4x writes): 18 + 36 + 3 = 57 for one server on a default Postgres; 4 + 8 in dev; CLI commands without a server 2 + 2. Worker 0 logs `Postgres connections: … of the N Postgres allows` and warns above 80%. Set both sizes yourself only when other apps share the database, and then keep `REPLICAS x that` under `max_connections` with room for a reload's second process and `psql`. `sorry, too many clients already` logs, once a minute, which settings decide the count.

**`RUNTIME_WORKERS` is not scaling out.** It adds function-runtime processes on one server (switches `RUNTIME_MODE` to `process`; one call goes to the process with the fewest waiting). It helps CPU-heavy functions, hurts light ones (each call crosses a pipe: about 2x CPU), and SQLite writes still share one lock. Default 1; `auto` = floor(cores x ratio). Postgres pools are split across the workers automatically (above); with sizes you set, every worker holds both of them. On the dashboard Settings page a worker change applies live in `process` mode; inline <-> process needs a restart.

SQLite facts: WAL mode, one writer, belongs to one engine process (a second engine on the same `app.db` gives `database is locked` after 5 s). Past about 600 mixed requests/s per core, add processes or move to Postgres. Inline mode (production default) runs functions in the server process: a function that never yields is killed by a watchdog after timeout + 5 s together with the whole process, so always run under a restart policy. `DATA_DIR` must be on a persistent volume.

## Backups and restores

One `.tar.gz`: `manifest.json`, all documents (`data/documents.jsonl`, the same format as `export`, auth tables and `_storage` included), scheduled jobs and migration state, `config/env.jsonl` + `settings.jsonl` **with values**, the `forge/` source, and the files every `_storage` row names. Not included: dashboard accounts/sessions/audit log, telemetry, the process environment (`.env`). It holds password hashes and secrets: treat as secret (only owners download or restore). The snapshot is one read transaction; writes continue.

- **Where** (first that applies): `BACKUP_S3_ENDPOINT`+`BACKUP_S3_BUCKET` (+keys, region, prefix; a bucket of their own, the production choice) > `BACKUP_DIR` > the files' bucket under `_backups/` (with `STORAGE=s3`) > `DATA_DIR/backups` (inside the `app-data` volume: lost with the disk).
- **Schedule:** `BACKUP_SCHEDULE` cron in UTC (`0 3 * * *`; `@daily` works), `BACKUP_KEEP` (default 7, scheduled ones only), `BACKUP_FILES` (default on). Applies within 30 s, no restart. Run on every server, made once; a missed slot runs once on return.
- **Make one:** `archlast-forge backup before-upgrade.tar.gz` (`--no-files` skips files), or the dashboard's Back up now. Any other file name is the older SQLite-only copy (`VACUUM INTO`; Postgres refuses and points to `pg_dump`).
- **Restore:** `archlast-forge restore before-upgrade.tar.gz [--no-files] [--config]` or the dashboard (owner; type `restore`). Order: a safety backup of the current state first (failure aborts), then files, then **all schema tables emptied and refilled in one transaction**, validated by the schema running now (one bad document rolls everything back: `Document posts:… doesn't fit the schema… Nothing was restored.`), then every server drops its cache and reruns subscriptions. `--config` also restores env vars and settings (off by default so a restore into another deployment keeps its keys; reload the runtime for env vars, restart for settings). Code is **not** restored (the source is in the archive). A table the backup has and the schema doesn't is refused: deploy the matching code first. Writes wait during the transaction: restore large backups at quiet times.
- Works across databases (SQLite backup restores into Postgres and back). Dashboard upload limit is `MAX_UPLOAD_MB`; restore larger archives with the CLI. Restore one table: take `data/documents.jsonl` from the archive and `import --replace` the lines you want.
- A SQLite file copy of `app.db` alone can miss WAL data: never `cp` it while the engine runs. Test a restore at least once. Not supported: point-in-time recovery (use Postgres' tools), incremental backups, encryption (encrypt the bucket/disk).

## Upgrades and deploying changes

- **Versions move in lockstep**: every `@archlast/forge-*` package, `create-archlast-forge` and the engine image (`ghcr.io/algochad/archlast-forge-engine:<version>`) share one version; the image is built on the CLI's version, so updating the CLI updates the engine. `archlast-forge upgrade [version]` rewrites versions in `package.json` and `forge/package.json` (keeping `^`/`~`), the engine tag in `Dockerfile` and `compose.yaml`, adds Prettier setup if missing, installs, and reruns codegen with the new CLI. In a monorepo run it from the root: every app, service and shared package moves together. Versions it cannot find on the registry change nothing. If `bun install` fails the files are already changed: fix and `bun install` again.
- Order: **backup**, commit a clean tree, `upgrade`, `bun run typecheck`, tests, commit (`forge/_generated` too), then `archlast-forge up` (rebuilds on the new engine image). Projects on 0.9.0 or older lack `upgrade`: `bunx --package @archlast/forge-cli@latest archlast-forge upgrade`.
- **Schema changes:** documents are JSON, so adding a field or table needs no migration step. But outside dev startup validates every document against the schema and refuses to start on a mismatch. Make changes in steps: add the field as `v.optional`, run a data migration that fills it (`archlast-forge migrate --run-migrations`; `--status` lists them), deploy, then make it required. To get an app back up first: start once with `SCHEMA_CHECK=off`, fix, turn it back on. `archlast-forge migrate` prints up to 50 offending documents.
- **Compatibility during rolling deploys:** old and new servers run side by side; keep function changes compatible both ways. A deployed full-stack app replaces hashed `/_app` files: an open tab navigating to an unloaded chunk fails until reloaded (HTML is never cached).
- One container restart is a few seconds of 503/refused requests; WebSocket clients reconnect and refetch; scheduled jobs that came due run after; **cron slots inside the gap are skipped**.

## Logs, metrics, dashboard (pointers)

- Logs: stdout/stderr, JSON per line in production (`time`, `level`, `msg`, `requestId`, `function`). `archlast-forge logs app` or `docker compose logs -f app`. Every response has `x-request-id`; a client's `Server error (request <id>)` is that id: search the log for it, or paste it into the dashboard's Ctrl+K search to open the trace.
- `GET /metrics`: Prometheus text, `Authorization: Bearer $METRICS_TOKEN` (or `ADMIN_KEY`), per server. Useful series: `forge_function_calls_total`, `forge_function_errors_total`, `forge_function_duration_ms_bucket`, `forge_websocket_connections`, `forge_subscriptions`, `forge_process_resident_bytes`, `forge_event_loop_delay_ms`, `forge_runtime_queue_waiting`; with the firewall on, `forge_waf_requests_total{result=inspected|blocked|detected|errors}` and `forge_waf_rule_matches_total{rule}`.
- The dashboard (`/_dashboard`; on in dev and in the generated stack, off for `start` and images unless `DASHBOARD=on`): requests, traces, errors, logs, data editor, functions runner, files, jobs, backups, settings, audit, the firewall (Firewall page) and the security headers with their CSP reports (Security page). Roles viewer < admin < owner; sign in with a named account (`admin add`) or `ADMIN_KEY`. In production fence it (VPN or IP allow-list at the proxy) and keep `ALLOW_CUSTOM_FUNCTIONS` off. Details: [dashboard-and-observability.md](dashboard-and-observability.md).

## Common mistakes

- Putting a variable in `.env` and expecting the container to see it (compose passes only listed names).
- Running `start`/`up` outside dev without `BETTER_AUTH_SECRET`, or with an http `BETTER_AUTH_URL` and no `ALLOW_INSECURE_HTTP` (and shipping `ALLOW_INSECURE_HTTP=1` to real users).
- Setting `DASHBOARD=enabled` (booleans need `on`/`1`/`true`/`yes`; this is off) or leaving the dashboard and `ALLOW_CUSTOM_FUNCTIONS` open to the internet.
- Forgetting `TRUST_PROXY=1` behind a proxy, or setting it where nothing overwrites `X-Forwarded-For`.
- `REPLICAS > 1` with SQLite, without Redis, or with `STORAGE=local`; backups to a folder on one server.
- Using `RUNTIME_WORKERS` as horizontal scaling, or setting `RUNTIME_MODE=inline` with workers or in dev.
- Treating `env set` as a way to change engine settings (`PORT`, `BETTER_AUTH_SECRET`, `S3_*`): they come from the environment or the Settings page.
- Rewriting paths in the proxy, or not forwarding `/rpc` WebSocket upgrades.
- Adding security headers at the proxy as well as the engine, or turning `HELMET=off` to fix one blocked script (give it the nonce or add its source instead).
- Setting `DATABASE_POOL_SIZE`/`DATABASE_WRITE_POOL_SIZE` "for performance": every runtime process of every server holds all of both from start.
- Turning on `WAF=on` in block mode directly on live traffic; run `WAF_MODE=detect`, read the Firewall page, then block.
- Renaming `name:` in `compose.yaml`, or `down --volumes`, without a backup.
- Copying `app.db` while the engine runs instead of `archlast-forge backup`.
- Making a required schema field in one step on a database that has old documents.
- Upgrading packages by hand so CLI, packages and the engine image disagree on versions: use `archlast-forge upgrade`.
- Running data commands against a remote stack from your laptop and trusting the `✓` (they may have hit local SQLite).
